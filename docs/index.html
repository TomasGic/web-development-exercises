My deployment workflow

  1. Start clean from an up-to-date main branch
    • cd web development exercises
    • git status
    • git switch main
    • git pull
  2. Create a new workspace branch, for example week-08-public-artifact
    • git switch -c feat/projects-section
  3. Commit small changes locally
    • git status
    • git add docs/index.html
    • git commit -m "feat(pages): add portfolio homepage markup
  4. Publish the working branch to Github
    • git push origin week-08-public-artifact
  5. Create a pull request on Github, review the changes and merge workspace branch into main. The merge triggers the deployment

Key lessons learnt from the deployment process

  1. The main branch is production

    2. It might feel tempting to push code changes directly to the main branch, but this is risky, because pushing changes directly to main will automatically update the live site and might potentially break it. When adding a new feature to the website, it is important to adopt the workflow outlined in the section above. This ensures that any new changes are made in isolation and do not touch the main branch.

  2. Absolute vs relative paths

    3. When referencing filepaths in the codebase, it is important to use relative paths instead of absolute paths. By relative, I mean relative to the file being edited. No path should ever start with "/".

  3. Git isn't just a tool for backing up code

    4. Since I started working with Git and Github more regularly as part of my web development workflow, I realised the importance of separating features into distinct commits with clear and meaningful commit messages.I believe this is a skill that requires a lot of attention and serious practice. A clear commit history makes it much easier to debug and revert changes if something breaks and servers as an audit trail for other developers who are working with the same repository.
